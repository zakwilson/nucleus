## Stage 15 W4a — located name-resolution diagnostics (2026-07-25)

Spec: [stage15-stress-test/diagnostics.md](stage15-stress-test/diagnostics.md)
§W4a (with a "W4a as built" addendum correcting the doc's stated ground truth).

**No compiler diagnostic reports `:0:`.** All seven confirmed line-0 cases now
name the line of the reference. 211 tests pass; `make bootstrap` is
byte-identical (stage1 == stage2) with no reconverge, as a diagnostics-only
change must be.

- **Root cause** was not "a registration phase lost the node" but the reader:
  `read-form` **interns** symbol nodes, so all occurrences of a spelling share
  one `Node` whose `line` is 0. Any diagnostic whose subject is a symbol had
  nothing to report. Interning cannot be removed (symbol identity is compared
  by pointer throughout the compiler), and a line must never be *written* into
  a symbol node — which the compiler was doing: `stamp-macro-lines` stamped
  symbol children with the macro call site's line, so after the first expansion
  mentioning `x`, every diagnostic anywhere about any `x` reported that call
  site. Now skipped.
- **Fix, two mechanisms.** ~110 raise sites borrow the enclosing form's line via
  a new `node-line` helper (`lib/node.nuc`) — the enclosing node is already in
  hand at each. `emit-symbol-ref`, reached from `emit-node` with only the
  operand and with 98 `emit-node` call sites upstream, instead takes an explicit
  `line:i32` filled from `g-form-line`, an ambient enclosing line maintained
  with strict save/restore in `emit-node` (the single dispatcher) — the same
  shape as the already-ambient `g-source-path`/`g-mono-context` that `die-at`
  reads for the other two components of a location.
- **Did-you-mean** over generics/macros/type-names/globals by Levenshtein
  distance, with a length-scaled allowance (`< 4` chars none, 4-6 one edit, 7+
  two) so short names never draw a coincidental match, plus a small
  wrong-mental-model table (`bit-not` → `(bit-xor x -1)`).
- **Regression protection**: `run_no_line_zero` compiles every
  `tests/fixtures/*.nuc` and fails on any `:0:`; `run_reject` now fails on `:0:`
  for every existing and future rejection test; `run_reject_at` pins
  message + `<path>:<line>:` for five new fixtures. Both guards verified against
  a negative control (reintroduce the bug → they fail; restore → they pass).
- **Incidental**: `boot/nucleusc.ll` had been un-buildable since
  `04c55ec Merge stage14` — the merge duplicated the `@emit-keyword` definition,
  so `clang` rejected the module and any fresh checkout failed at
  `make boot-binary`. Repaired (deleted the stale copy, which also carried a

## Stage 15 W4b — `defconst` annotation rejected + sibling-definer sweep (2026-07-25)

Spec: [stage15-stress-test/diagnostics.md](stage15-stress-test/diagnostics.md)
§W4b (with a "W4b as built" addendum recording the sweep table).

lookupable name `K` — `desugar` never rewrites a `defconst` name, so the whole

  whose name is never annotated** (`defenum`, `defstruct`, `defprotocol`,

  exact defect class W4a exists to eliminate, missed there because a
  colon-annotated `defstruct` name wasn't among W4a's six confirmed cases).

  "missing :type" diagnostic (the plausible mistake for the one definer whose
  annotation is *required*) was correctly worded but reported line 0 —

## Stage 15 W2b — a named integer constant behaves like the literal (2026-07-26)

Spec: [stage15-stress-test/literal-typing.md](stage15-stress-test/literal-typing.md)
§W2b (with a "W2b as built" addendum). Closes findings §3.1 and §3.8; W2c's
doc-only correction landed in the same doc pass.

**§3.1.** `(defconst K 512)` + `(<= ans:ui32 K)` died `mixed signed/unsigned
operands` while the identical program spelled `(<= ans:ui32 512)` compiled —
naming a constant changed how it typed, and the Doom port wraps constants in
helper functions because of it. `emit-defconst` registered the name as an
ordinary global `Sym` and `emit-symbol-ref` returned a concretely-typed `i32`
`Val` with no literal provenance, so `binop-result-type` saw a typed operand.
Fixed by carrying provenance on the `Sym` — `const-lit` plus `const-lit-i64`,
the **value** and not just a flag — set by `emit-defconst`/`emit-defenum` (and
the REPL's hand-registered `NODE-*` mirror), deliberately not by `deferror`
(`is-int-type` is true for `TY-ERR`, so an `Err` constant would otherwise have
begun unifying with plain integers). The type rule stays in exactly one
function: `binop-result-type` gained a `scope` parameter and calls one new
predicate, `operand-is-int-literal`. The scope is **threaded** (through
`binop-coerce` and `emit-binop-vals`, whose two callers both already had one)
rather than shortcut to `g-globals`, because a local binding shadows the
constant and a shadowed local is not a literal.

**The silent wrong answer.** `emit-defconst` hardcoded `ty-i32` while
`const-val` carried the full decimal string, so `(defconst BIG 5000000000)` +
`(let (x:i64 BIG) …)` printed `705032704` — exactly the wrap LW-4 had already
fixed for inline literals. Constants are now typed at `emit-int`'s truthful
width, shared as `int-literal-type` and called from all three former copies of
that `if` (`emit-int`, `emit-defconst`, `node-type`'s `NODE-INT` branch).
Carrying the value also arms the existing `coerce-int-val` range check. A
**second, pre-existing narrowing hole** surfaced while fixing it: `defvar-init-ir`
hands a decimal string straight to LLVM as a global initializer, and LLVM
truncates `i32 5000000000` to `705032704` without complaint — closed for the
named *and* the inline spelling.

**`defenum` decision:** members get the same treatment. An enum member carries
no distinct nominal type (its `Sym` type is plain `i32`; `match` exhaustiveness
keys off the `EnumDef`), so withholding provenance would recreate the identical
wart one level over — `(= c:ui32 GREEN)` rejected while `(= c:ui32 1)` compiles.
`node-is-int-literal`'s other five call sites — the multimethod-dispatch
`is-lit` flags in `src/generics.nuc` — were deliberately left alone: those
decide overload *selection*, and widening the literal set there would silently
re-route existing dispatch.

**The trap.** The variadic operator macros wrap the tail, so `(* v K)` expands to
`(_* v (* K))` and a binop's **second** operand node is a CELL, never the bare
symbol. `node-is-int-literal` macroexpands a CELL for exactly this reason; the
first cut of `node-is-const-int-literal` did not, and the fix worked in
operand-1 position while silently not working in operand-2 position —
reintroducing the very operand-order asymmetry W2a existed to remove, in a form
the §3.1 repro (which uses `<=`, not a macro) cannot catch. Recorded in
`context/conventions.md`.

**Premise corrections.** The spec's constraint "constants that do not fit `i32`
are stored `i64` today" is **false** — they were stored `ty-i32` and wrapped.
W4b's rejection of `(defconst K:i32 512)` does leave W2b unconstrained on the
annotated-constant question (confirmed against the compiler, not assumed). The
brief's worry that tagging the Val `is-lit` could change **vararg** behaviour
did not materialize, for a structural reason: every `is-lit` reader on that path
is conjoined with `type-is-strview`, so an integer Val is fenced out by type.

`make test`: **240/240** (235 → 240). `make bootstrap`: stage1 == stage2
byte-identical on the first pass, no `update-bootstrap` — no `defconst` in

binops are either same-type or against `i64`/`usize`, where "adopt the other
operand's type" and "widen to the wider" agree.


## Stage 15 W2d — float literals adapt to an `f32` target (2026-07-26)

Spec: [stage15-stress-test/literal-typing.md](stage15-stress-test/literal-typing.md)
§W2d (with a "W2d as built" addendum). Closes finding §3.6 and completes W2.

**The finding was bigger than "float literals do not adapt."**
`coerce-int-val` (`src/abi.nuc`) — despite the name, *the* implicit-coercion
chokepoint for `ptr`/`CStr`/`StrView` and integers alike — had **no float case
at all**, and its callers do not agree on what a null return means. Eight
typed-slot positions read null as a type error and rejected an `f32` target
(`let`/`with` init, `set!`, `.set!` field store, explicit **and implicit**
`return`, struct-literal and array initializers — positional and designated are
separate call sites; the brief listed five). The ninth, the argument loop in
`emit-call-with-args`, reads null as "leave the argument alone" and therefore
**silently miscompiled**: `(take 2.5)` against `(defn take (x:f32):f32 …)`
emitted `call float @take(double 2.5)`, parsed fine, and printed `0.000000` —
for a non-literal `f64` argument too.

**A third bug, in the position recorded as already working.** LLVM accepts a
decimal constant for `float` only when it round-trips exactly, so
`(defvar g:f32 1.5)` worked while `(defvar g:f32 3.14)` emitted
`@g = global float 3.14` and died `floating point constant invalid for type` at
IR-parse time. A global initializer is a *constant*, so unlike every value
position it cannot be repaired with an `fptrunc` instruction — it needs the
literal re-rendered at the target width (the hex form, `0x40091EB860000000` for
`3.14f`, matching clang byte for byte).

**The fix, at the one chokepoint.** `coerce-int-val` gains a float↔float branch:
a float **literal** is re-rendered as a constant at the target width with no
instruction; anything else gets `fpext`/`fptrunc`. `coerce-num-val` (binops) and
`safe-coerce-val` (call arguments) delegate to it rather than carrying their own
copies — the widening direction is byte-identical text, so existing programs are
unchanged. Carrier: `Val.is-flit`/`lit-f64`, deliberately separate from `is-lit`
(which already means "int literal" and, with a `StrView` type, "unmaterialized
string literal", and whose readers sit on the vararg path where floats appear).
Three renderers in `src/nucleusc.nuc` beside `float-literal-ir`:
`float-literal-value`, `f32-const-ir`, `float-literal-ir-at`.

**Decision: Option A** — a non-literal `f64` narrows into an `f32` target
silently. Not a new policy: `coerce-int-val`'s integer branch five lines up
already truncates a typed `i64` into an `i32` slot at these exact positions
(measured — `(let (b:i64 300000000000 a:i32 b) …)` prints `-647710720` today)
and range-checks only literals. C converts implicitly at every one of these
positions too. Option B would have made floats the only kind behaving
differently at the shared chokepoint. The `as`-refuses-what-assignment-accepts
tension Option A inherits is **not float-specific** (`(as i32 n:i64)` is refused
while `(let (a:i32 n) …)` truncates) and is documented as one language-wide
question, not resolved in one direction for floats alone.

**Dispatch is deliberately stricter than assignment.** `arg-adapts` now admits a
float *literal* into a narrower float parameter — without it a solitary
`(defn take (x:f32) …)` accepted `(take 0.1)` while an overloaded one reported
`no matching method … (f64)`, the same wart one level over W2b closed for
`defenum`. Strictly additive (tier 0 still claims an exact `f64` overload first,
so no existing call is re-routed). A typed `f64` **value** still does not adapt:
dispatch selects *which function runs*.

**`-ffast-math` came off the compiler's own link line.** Folding a literal at
compile time evaluates it in the compiler process, and `-ffast-math` pulls in
`crtfastmath.o`, setting FTZ/DAZ process-wide — so every denormal single folded
to zero (`(defvar d:f32 1e-45)` → `float 0x0000000000000000` where clang emits
`0x36A0000000000000`). Fixed at the root in the Makefile with the reason
recorded there. Emits no IR change, so the bootstrap is unaffected.

**Accept criterion met.** `tests/fixtures/w2d-dsp-biquad.{nuc,c}` — a
direct-form-I biquad with all coefficients as bare float literals, no cast
anywhere — is **bit-exact** with the equivalent C program at `-O0` and `-O2`,
compared as raw 32-bit patterns. Two things are load-bearing and commented in
both files: every expression is an explicit *binary* tree (Nucleus's variadic
`+`/`*` are right-associative, C's are left-associative) and the C side uses
`-ffp-contract=off`. The Nucleus side goes through the real compile-and-link
path — `--emit-llvm` never parses the IR it writes, which is exactly how the
invalid-constant and mismatched-operand bugs stayed invisible.

**Known interaction, not a regression:** on `--target=avr`, `avr-reject-f64`
fires inside `emit-float` before the target width is known, so a float literal
is rejected even in an `f32` slot. This predates W2d — `(unsafe/cast f32 1.5)`
hit the identical rejection — so an AVR program has never been able to spell a
floating-point constant. `make avr-test` green.

`make test`: **245/245** (240 → 245). `make bootstrap`: stage1 == stage2
byte-identical on the first pass, no `update-bootstrap` — the compiler's own
source has no `f64`→`f32` coercion, so the new branch is inert for it.
`make avr-test`, `make abi-test`, `make layout-test` also green.


## Stage 15 W3a — opaque forward-declared C types (2026-07-26)

Spec: [stage15-stress-test/cheader.md](stage15-stress-test/cheader.md) §1.6
(with a "W3a as built" addendum). Closes finding §1.6; W3b (§1.5) and W3c (§1.4)
remain open.

**The gap.** `src/cheader.nuc` skipped a bodyless `struct Foo;` outright, so the
type never registered and any later `ptr:Foo` died `unknown type: Foo`. That is
C's opaque-handle idiom — every SDL handle type, `Mix_Music`, and `FILE` (glibc
defines `struct _IO_FILE` with bitfields the C parser cannot model, so the tag
never gets a layout) — and it is why the Doom port hand-mirrors every opaque
type.

**Representation.** `StructDef.opaque` means *the name is known, the layout is
not*. It is cleared in **`struct-set-fields`** (`src/abi.nuc`), the single
chokepoint every field-populating path funnels through, so "acquires a layout"
and "stops being opaque" cannot drift. `StructDef.alias-of` links a C
`typedef struct Tag Name;` alias entry to its tag (`lookup-struct` is keyed by
name, so an alias must be its own StructDef). An opaque entry is deliberately a
*different* state from a name-only pre-registration by `prescan-struct-names`,
whose layout arrives later in the same unit.

**Legal use is exactly what C permits.** `ptr:Foo` / `(ref Foo)` / `(raw Foo)`
work everywhere, including in a `defn` signature. Every by-value use is refused
at six sites — `emit-sizeof`, `emit-alloca-form`, both field-access paths
(`emit-field-get` and `emit-get-intrinsic`, beside the existing
`union-field-guard`), `emit-defn`'s parameter loop and return type, and
`emit-defstruct`'s field loop — each with a node in hand, so the location is
exact; plus a backstop in `type-to-ir`'s TY-STRUCT/TY-UNION branch on the ambient
`g-form-line`, so no path can put an undefined `%Foo` into an IR stream and turn
a source mistake into an LLVM parse error thousands of lines later. A size is
never guessed. The message names the C declaration too — `sizeof: 'CHOpaque' is
an opaque type declared at ./foo.h:11; only pointers to it are valid` — from
clang -E's `# N "file"` linemarkers, which the header scan now records (before
this, a cheader StructDef recorded the importing `.nuc` file and line 0).

**A later definition upgrades in place**, through one shared emitter, in all
three orderings real headers use: `struct Tag;` then `struct Tag { … };`
(the already-registered branch used to `return existing` untouched, which would
have pinned the tag opaque forever); then via `typedef struct Tag { … } Name;`,
which parses its body *anonymously* and never registered the tag at all; and a
`typedef struct Tag Name;` alias registered while the tag was still opaque.

**Two premises in the spec were wrong.**

1. *"The fix is small and local: one branch."* `c-parse-type` had to be taught to
   keep returning `ptr` for an **opaque** tag. Its `struct Tag` lookup is reached
   only for a *by-value* `struct Tag`, and it returned `ty-ptr` for an
   unregistered tag; registering opaque types without that guard would have made
   those `TY-STRUCT` and emitted `declare void @f(%Tag)` for an undefined `%Tag`
   — trading a wrong-ABI pointer for invalid IR, i.e. manufacturing more of the
   §1.5 failure this stage exists to remove.
2. *The spec's own §1.6 probe cannot pass from import-time registration at all.*
   `(defn f (w:ptr:SDL_Window):i32 …)` resolves its types in
   `prescan-defn-signatures`, which runs **before any import is processed**, and
   `prescan-imported-types` deliberately skips C-string imports. W3a therefore
   adds `cheader-prescan-opaque`, a name-only scan hooked into
   `prescan-imported-types` that registers exactly the names the real import will
   define — so the real import upgrades the same entries and emits the same single
   type definition. This also removed the neighbouring asymmetry where
   `ptr:Mix_Music` resolved in a signature but the fully-defined `ptr:Mix_Chunk`
   did not.

**`unknown type:` gained a location.** The prescan resolved a signature's types
against the defn's **name** node — an interned NODE-SYM whose line is always 0 —
and `desugar-typed` stamped every desugared binding cell from the same kind of
node. Both now borrow the enclosing form's line, which gives a real line to every
diagnostic raised off a `defn` parameter, a `defvar`/`extern`/`declare` name, a
`defstruct` field, or a `let`/`with` binding name; the parameter case reports the
parameter *list's* line.

**Incidental fixes.** `MAX-STRUCTS` 256 → 1024: the cap used to bound a program's
own types, but opaque registration makes the registry scale with *header* size —
measured, `SDL.h` + `SDL_mixer.h` + `png.h` in one unit needs between 200 and 256
slots. And preprocessed header text is now cached by path (a C header import is
deliberately not deduplicated, so a header was preprocessed once per
`(import-use …)` naming it): 5 clang invocations → 3 for a `hello.nuc` build,
~30% faster end to end than before W3a rather than ~40% slower. Sharing the
buffer surfaced that `emit-c-include` ended with **`(free buf)`** — correct with a
per-call buffer, a use-after-free once shared, and it presented as a *hang* (the
parser looping over garbage) only on the **second** import of the same header.

`make test`: **255/255** (245 → 255). `make bootstrap`: stage1 == stage2
byte-identical on the first pass, no `update-bootstrap`. Because W3 touches
shared code, inertness was verified beyond the fixed point: `make lib-cheaders`,
`make lib-headers`, and the emitted LLVM IR of **every** `lib/*.nuc` and
`examples/*.nuc` are byte-identical against a compiler built from the pre-change
tree.

## Stage 15 W3b — C type qualifiers + the `declare` validity gate (2026-07-26)

Spec: [stage15-stress-test/cheader.md](stage15-stress-test/cheader.md) §1.5
(with a "W3b as built" addendum). Closes finding §1.5; W3c (§1.4) remains open.

**The finding was not about `void`.** `c-parse-type` accepted C type qualifiers
only in **leading** position. A qualifier *after* the base type — "east const",
which C permits and which denotes exactly the same type — terminated the type;
its token was then consumed as the parameter's **name**, leaving the following
`*p` to begin a phantom **second** parameter that defaulted to `ptr`:

| C declaration | emitted (before) |
|---|---|
| `void _mm_clflush(void const *__p);` (via `SDL2/SDL.h` → intrinsics) | `declare void @_mm_clflush(void, ptr)` |
| `void f(int const *p);` | `declare void @f(i32, ptr)` |
| `void f(struct Op const *p);` | `declare void @f(ptr, ptr)` |
| `void f(int const n);` — no pointer at all | `declare void @f(i32, ptr)` |

Only the `void` row is invalid IR. Every other row is **representable but
wrong** — wrong arity, wrong ABI, no diagnostic at any stage — which is the
design point worth carrying forward: **a validity gate cannot catch this class**
(`(i32, ptr)` passes any reasonable gate), so the parse fix is the primary
deliverable and the gate is the safety net for what remains. Fixed with
`c-skip-type-quals` (`src/cheader.nuc`), called once after the
declaration-specifier loop (covering builtin, typedef-name and `struct Tag`
bases alike) and once after every `*`; `const`, `volatile`, `restrict`,
`__restrict`, `__restrict__` and `_Atomic` are consumed and discarded rather than
modelled, since the emitted LLVM type is identical either way.

**The gate.** `c-decl-skip-reason` runs on every *recognized* function
declaration, before registration and before the collect-mode alias push (aliasing
an unregistered name would leave a dangling `prefix/name`). Four arms: a by-value
struct/union with no known layout (signalled by a declaration-scoped
`g-cheader-unrep` set inside `c-parse-type`, cleared for a function-pointer
parameter and for an array parameter — glibc's
`utimensat(int, const char *, const struct timespec [2], int)` is what proved
that arm necessary); a recorded `void` parameter (`void` is legal only as the
whole empty list, which is consumed before any parameter is recorded); an opaque
parameter or return type; and an arity over `C-MAX-PARAMS` (32 — the count keeps
incrementing past the array's capacity so the gate sees the real arity and skips
rather than registering a truncated signature; the array was 16 and was being
written past). The declaration is still consumed, so the caller does not rescan
it. The gate deliberately sits *after* recognition: the "not a function
declaration at all" path stays silent, since every typedef, variable and `static
inline` body in a preprocessed header goes through it legitimately.

**Warning policy.** `<header>:<line>: warning: skipping C declaration '<name>':
<reason>`, located in the C header (via W3a's linemarker machinery) rather than
the `.nuc` that imported it. Always on, no flag; deduplicated by function name
(imports are deliberately not deduplicated and umbrella headers include each
other transitively). Measured volume is **zero** across `<stdio.h>`,
`<stdlib.h>`, `<string.h>`, `<unistd.h>`, `<fcntl.h>`, `<math.h>`, `<time.h>`,
`<sys/stat.h>`, `<pthread.h>`, `<netinet/in.h>`, `<signal.h>`, `png.h`,
`SDL2/SDL.h` and `SDL2/SDL_mixer.h`.

**A third root cause, found by measuring instead of trusting.** A stray `)` —
present since `6ef16dc Add union types` — closed `emit-c-include`'s top-level
dispatch `cond` after its first clause, leaving `true` a bare no-op statement and
running the function-declaration parse **unconditionally**. So after every
top-level `struct`/`union`/`typedef` a function parse ran in the same iteration,
starting at the whitespace the type parse stopped on: the next declaration's
warning named the *type declaration's* line, and a second consecutive forward
declaration (`struct Foo;` then `struct Bar;`) was eaten by the stray parse's
not-a-function fallback without being registered. A dangling `true` at the end of
a `cond` is the syntactic tell — as a statement it is dead code, so it never
appears deliberately.

**Premises corrected.** The spec's suggested "no unresolved type names" gate arm
is not implementable and would be wrong: an unfollowed typedef resolves to `ptr`,
which *is* representable, so such a gate would skip a large fraction of every
real header (that is §1.4's defect, to fix at the source). And "compiler-internal
headers must still pass the gate" is **false** — 3 of 33 `make lib-cheaders`
outputs produce 11 skips, every one a genuine `--emit-cheader` defect: it emits a
parametric template's **type variable** as a C type (`void conj(void* self,
struct T elem);`), which is not describable in C at all. The gate is right;
`--emit-cheader` is wrong. (Same family as the hyphenated-identifier defect W3a
recorded in the same files.)

**Header ladder: rung 2 reached.** `SDL2/SDL.h` imports with zero warnings and
1663 declarations, and the spec's two-line probe compiles, **links and runs** —
verified with `-o` and `llvm-as`, never with `--emit-llvm`'s exit code, which
never parses the module it writes.

`make test`: **258/258** (255 → 258). `make bootstrap`: stage1 == stage2
byte-identical on the first pass. `make lib-cheaders` output and the emitted IR
of every `lib/*.nuc`, every `examples/*.nuc` **and the compiler's own
`src/nucleusc.nuc`** are byte-identical against a compiler built from the
pre-change tree.


## Stage 15 W3c — C typedef chains + declaration precedence (2026-07-26)

Spec: [stage15-stress-test/cheader.md](stage15-stress-test/cheader.md) §1.4
(with a "W3c as built" addendum). Closes finding §1.4 and **closes W3**.

**The finding was broader than "`off_t`'s chain degrades somewhere".** No scalar
typedef resolved *at all*: `c-parse-type` returned `ptr` for every name it did
not recognize as a builtin, and `c-type-to-nucleus` hardcoded exactly two
(`size_t`, `ssize_t`). A one-level `typedef int myint;` degraded as thoroughly as
`off_t`'s three-level chain, in return types, parameters **and struct fields**:

| declaration | before | after |
|---|---|---|
| `off_t lseek(int, off_t, int)` | `declare ptr @lseek(i32, ptr, i32)` | `declare i64 @lseek(i32, i64, i32)` |
| `ssize_t getline(char**, size_t*, FILE*)` | `declare ptr @getline(ptr, ptr, ptr)` | `declare i64 @getline(ptr, ptr, ptr)` |
| `int fseeko(FILE*, off_t, int)` | `declare i32 @fseeko(ptr, ptr, i32)` | `declare i32 @fseeko(ptr, i64, i32)` |
| `struct timeval { time_t; suseconds_t; }` | `%timeval = type { ptr, ptr }` | `%timeval = type { i64, i64 }` |
| `Mix_Chunk { int; Uint8*; Uint32; Uint8; }` | `{ i32, ptr, ptr, ptr }` | `{ i32, ptr, i32, i8 }` |

The struct rows are the worst: a wrong **layout**, silently, with every field
after the first mistyped one at the wrong offset.

**The table.** `c-parse-typedef-decl` (`src/cheader.nuc`) records a non-aggregate
`typedef`, reached from the top-level dispatch only after `c-parse-struct-decl`
declines — so W3a's opaque-registration and in-place-upgrade paths are untouched.
Resolution happens **once, where the `typedef` is parsed**, and the table stores
the resolved `Type*`: a chain costs one lookup at each use, and a cycle is
impossible by construction (an entry can only resolve against entries recorded
strictly before it, so `typedef foo foo;` records `foo` as unrepresentable rather
than looping). Covers scalars at any depth, pointers, function pointers
(recognized *before* the declarator fallback, or `typedef int (*h)(int);` parses
as a function literally named `int` — W3b's flagged trap), enums, and
struct-alias typedefs. Two neighbouring gaps had to go with it: **`enum` was not
a declaration specifier at all** (`enum Tag e` read `enum` as the base type and
`Tag` as the declarator, the same phantom-parameter shape W3b found for east
qualifiers), and **`__extension__` was not consumed at top level** (glibc writes
`__extension__ typedef long long int __quad_t;` for every `long long` type).
`size_t`/`ssize_t` stay hardcoded deliberately: `clang -E` preprocesses for the
*host* even under `--target=`, so the table's answer would silently follow the
preprocessing host rather than the emission target.

A typedef the parser cannot follow is **never a silent `ptr`** — it is recorded
as known-but-unrepresentable and any by-value use is skipped. That finally makes
W3b's deferred "no unresolved type names" gate arm implementable, and it is now
in; a *pointer* to an unresolvable type is deliberately still `ptr`.

**Precedence.** Measured, both orders were silent **and disagreed**: *first*
wins, not the spec's "last wins" — so `(import-use "unistd.h")` above a
hand-written `lseek` silently discarded the author's declaration. Now an explicit
`(declare …)` wins in **both** orders (`prescan-explicit-declares` collects the
unit's declare names beside the other prescans, before any import runs), exactly
one `declare` reaches the module, and a mismatch warns naming both sources with
both rendered signatures. The non-obvious half: suppressing the header's copy is
not enough — it leaves the name undefined between the import and the declare
(`examples/cstr-lit-test.nuc` declares `strlen` at line 15 while `lib/arena.nuc`
calls it from inside the preceding prelude import), so the explicit declaration is
**emitted at the point of first need**.

**Two pre-existing defects surfaced, both unreachable until typedefs resolved.**
`c-parse-func-decl` never applied the aggregate C ABI (glibc names every by-value
aggregate through a typedef, and an unfollowed typedef was `ptr`, so the path had
literally never emitted a struct by value); it now routes through
`abi-classify`/`abi-ret-ir`/`abi-print-param` like `emit-nuch-declare-import`, so
`div`/`ldiv`/`lldiv`/`fopencookie` are ABI-correct and every scalar declaration
is byte-identical. And the cheader path never set `StructDef.emitted`, which
`pending-union-deps-ready` consults — so SDL's `SDL_WindowShapeParams` (a union
with an `SDL_Color` member) was deferred on every drain and never defined while
`%SDL_WindowShapeMode`, which contains it, referenced it.

**Warning policy split, because W3b's measurement changed.** W3b justified
always-on warnings with a measured volume of zero — a consequence of the §1.4
defect, since nothing *could* be detected while every unfollowed typedef was
`ptr`. With chains followed, `(import-use "SDL2/SDL.h")` reaches **165** genuinely
unrepresentable by-value declarations (149 `long double`, 7 `_Float128`, 6
`SDL_JoystickGUID`, 2 `SDL_GUID`, 1 `_Float16`), six of them in the REPL's
startup banner and six in every `make` of the compiler. So parse failures (W3b's
four arms) stay loud at import with their wording and dedup unchanged, while
"Nucleus has no such type" is recorded and delivered at the point of **use**:
`prog.nuc:12: error: unknown: 'strtold' — its C header declaration was skipped
(/usr/include/stdlib.h:127: a by-value 'long double' …)`. Strictly more precise
than a warning; nothing is silent.

Also took W3b's deferred musl item: `struct Tag *f(int);` without `extern` (glibc
always writes it, musl deliberately omits it) was silently dropped and is now
imported, with the fallback restricted to the `struct`/`union` tokens exactly as
W3b required.

**Header ladder closed.** Rung 1 (`<unistd.h>`/`<fcntl.h>`) reached end to end
and **runnable** — `examples/cheader-posix.nuc` drives open/write/lseek/read/close
through header imports alone, using `off_t` as an integer on both sides. Rung 2
(`SDL2/SDL.h`) still links and runs, now with 1497 declarations rather than 1663:
the 165 that went are the wrong-`ptr` ones that would have miscompiled if called.
Rung 3 (`SDL2/SDL_mixer.h`) reached, with `Mix_Chunk`'s `Uint8`/`Uint32` fields —
W3a's "newly observed, not fixed here" item — now correct. Remaining gaps, in
priority order: **array/bitfield/multi-declarator fields in a struct body** (what
keeps `FILE` and `SDL_GUID` opaque), the missing `long double`/`_Float128`/
`_Float16` types, and comma-separated typedef declarator lists.

`make test`: **261/261** (258 → 261). `make bootstrap`: stage1 == stage2
byte-identical after a boot reconverge (this change alters the compiler's own IR
— every C header it imports now yields correctly typed declarations).
`--emit-nuch` and `--emit-cheader` output for all 33 `lib/*.nuc` is
byte-identical to the pre-W3c compiler with the identical set of pre-existing
`--emit-nuch` failures, and `make lib-headers`/`make lib-cheaders` reach exactly
the same point they did before.


## Stage 15 W3c fallout — unnamed `declare` parameters carry types (2026-07-26)

Spec: [stage15-stress-test/cheader.md](stage15-stress-test/cheader.md), the
"Addendum to W3c" section. Surfaced by W3c, and a precondition for its
precedence rule being useful.

**`declare`'s parameter list ignored every written type unless the parameter was
named**, emitting `i32` instead:

| written | emitted |
|---|---|
| `(declare f1 (i64):i64)` | `declare i64 @f1(i32)` |
| `(declare f4 (f64 i64):i64)` | `declare i64 @f4(i32, i32)` |
| `(declare f5 (ptr i64 ui32):i64)` | `declare i64 @f5(i32, i32, i32)` |
| `(declare f6 (a:i32 b:i64 c:i32):i64)` | `declare i64 @f6(i32, i64, i32)` ← named: correct |

Return types were never affected, and the bare list was correct exactly when the
signature was all-`i32` — which is why it survived: `docs/toplevel.md` documents
the spelling and the compiler's own `src/nucleusc.nuc:16-17` uses it. Both
`(declare repl_print_f64 (ptr):void)` and its `f32` sibling emitted
`declare void @repl_print_f64(i32)` against a `src/repl_shim.c` shim taking
`void *`, correct only because x86-64 SysV passes a pointer and an `i32` in the
same register and because a call site's own signature governs codegen.

**Why W3c made it urgent.** W3c's rule is "an explicit `(declare …)` beats a
header-derived declaration, and a mismatch warns". With the defect, a bare-list
declaration that *agreed* with the header rendered as all-`i32`, so it conflicted
with every non-`i32` header signature, warned about a conflict that did not
exist, and the corrupted signature won — before W3c the header's correct
declaration would simply have been used, so this was a live regression in effect.

**The fix.** `emit-nuch-declare-import` (`src/nuch.nuc`) defaulted to `ty-i32`
whenever `extract-name-and-type` returned null — which it does for *any*
unannotated node, i.e. every bare type spelling. An unannotated element is now
parsed as a **type operand** (`declare-param-type`): a keyword through
`parse-type-name`, anything else through `parse-type-from-node`, both of which
already raise a **located** diagnostic, so an unresolvable spelling is an error at
its own line rather than a silent default.

An *annotated* element deliberately stays a named parameter, so
`(declare f (ptr:FILE):void)` declares a parameter *named* `ptr` of type `FILE`,
by value — the reading it has always had. Changing it would mean asking what the
head names (C's typedef ambiguity, with a keyword list to keep in sync with
`parse-type-from-node`) and would silently retype the `.nuch` generated for the
legal `(defn addone (ptr:i32):i32 …)`. Documented in `docs/toplevel.md` and
pinned by a test instead. `&rest`/`&optional` are now refused in a declaration:
none of the machinery exists (`variadic` is hardcoded 0, `has-rest` never set),
so the marker was counted as an extra `i32` parameter, and implementing it has
two incompatible meanings (Nucleus' cons-list `&rest` vs C varargs).

That refusal is the one non-additive part. **Three `tests/run-tests.sh` heredocs
used the spelling** — `(declare printf (fmt:CStr &rest args:i32) :i32)` in the
`n6`/`sm3`/`s1` `.nuch` link-and-run consumers — and were relying on the defect:
their calls pass 3–6 arguments to what the spelling made a 3-parameter
declaration, and call arity is not checked against a declaration. They now
declare the honest `(declare printf (fmt:CStr):i32)`; the extra arguments ride
the call site, which is how the C ABI passes them anyway. A tree-wide grep over
`*.nuc`/`*.nuch` cannot see heredoc-generated sources — the test suite is what
found them.

`make test`: **265/265** (261 → 265). `make bootstrap`: byte-identical after a
boot reconverge, and a clean rebuild from the committed boot IR reproduces it.
The codegen change was isolated by compiling **identical source** with the old
and new compilers: the diff is *exactly* the two `repl_print_f*` declarations
(six lines, no string-pool renumbering), and all **189** compiling
`examples/`/`lib/`/`tests/fixtures/` programs emit byte-identical IR — no
program in the tree used the bare spelling. All 33 `lib/*.nuch` regenerate

## Portability fixes — ARM64 Linux / LLVM 21 (2026-07-02)

**Two fixes for cross-platform builds**, verified on x86-64/LLVM19 (byte-identical bootstrap, 136 tests pass).

### Makefile: robust LLVM detection

The Makefile hardcoded `llvm-config` without `--link-shared`, which fails on Alpine ARM64 (LLVM 21) where only the monolithic `libLLVM-21.so` is available (no individual component libs). The `2>/dev/null` swallowed the error, leaving all LLVM vars empty → linker errors for every LLVM C API symbol.

**Fix:** auto-detect `llvm-config` across naming conventions (`llvm-config`, `llvm-config-21`, `llvm-config-19`, Alpine paths `/usr/lib/llvm21/bin/llvm-config`), with a three-tier fallback:
1. `--link-shared` (monolithic shared lib)
2. Static component libs (if shared unavailable)
3. Bare `-lLLVM` (if `llvm-config` missing entirely)

Added `--system-libs` (already in `build.ps1` but missing from the Makefile) for musl's extra deps (`-lz`, `-ltinfo`, etc.). A diagnostic line (`LLVM: config=... ldflags=... libs=...`) prints at build time for remote debugging.

### C header parser: musl compatibility

musl's libc headers (Alpine ARM64) omit `extern` on function declarations — valid C, since file-scope functions are implicitly `extern`. glibc includes it. The C header parser at `src/cheader.nuc:654` only tried `c-parse-func-decl` when the token was `extern`, so musl's `int strcmp(...)` was skipped → `unknown: strcmp` error when `lib/macros.nuc` used `strcmp` (imported via the prelude's `(import-use "string.h")`).

**Fix:** restructured the parser to try `c-parse-func-decl` for **any** non-struct/union/typedef token. `c-parse-type` already skips `extern`/`static`/`inline` internally (line 134), so both styles parse identically. If parsing fails (not a function), falls through to the skip logic.

Also added `_Noreturn` (C11 keyword) to the list of qualifiers skipped by `c-parse-type`. musl declares `exit` as `_Noreturn void exit(int)`, and the parser didn't recognize `_Noreturn`, treating it as the base type name → `unknown: exit` error.

### Test portability: null pointer printing

Two tests (`implicit-cast` and `macro-passthrough`) printed null pointers with `printf("%p", NULL)`. This is implementation-defined: glibc (x86-64) prints `0`, musl (ARM64) prints `(nil)`. Tests expected `0` and failed on ARM64.

**Fix:** changed both tests to cast the pointer to `i64` before printing with `%lld`, making output platform-independent. `examples/implicit-cast.nuc:28` and `examples/macro-passthrough.nuc:14` now print pointer values as integers.

Bootstrap artifacts refreshed (`make update-bootstrap`); the new compiler declares additional C functions (`lldiv`, `getentropy`, etc.) because it now parses non-`extern` declarations — expected, not a regression.

## Stage 13 — Lambdas and closures (2026-06-25)

**Stage 13 complete.** The four lambda/closure forms landed, split by capture

drop/lifetime semantics), closing the pre-existing `return &local` UAF; the

trivially-copyable types (hand-written for owning types); and a **structural
function-protocol conformance derivation** lets a closure or `fn` literal satisfy

## Stage 13 follow-up — Variadic `and`/`or` (2026-06-25)

**Variadic logical `and`/`or` landed** as prelude macros, mirroring the
`_+`/`+` split: `and`/`or` are now `&rest` right-fold macros in `lib/macros.nuc`
(`(and)`→`true`, `(or)`→`false`, `(and x)`→`x`, `(and a b c…)`→`(_and a (and b c…))`,
symmetrically for `or` over `_or`). The renamed binary short-circuit primitives
`_and`/`_or` are the actual special forms, routed to the existing
`emit-short-circuit` with unchanged IR labels, and are now **documented public
primitives** usable directly for hand-written binary short-circuit (same exposure
as `_+`).

**Cumulative narrowing is preserved** across variadic chains: the right-nested
binary spine means each clause narrows by all prior ones, so
`(and (!= m null) (m kind) (> (m x) 0))` typechecks (`(m kind)`/`(m x)` see `m`
non-null). The narrowing analyzers (`test-true-nonnull`/`test-false-nonnull`)
were retargeted from the old flat N-ary `(and…)`/`(or…)` loop to recurse both
arms of the new binary `_and`/`_or`.

**1-arg relaxation (accepted semantics change):** `(and x)`/`(or x)` now return
`x` **unchecked** (previously `(and x)` errored `"and expects 2 args"`). Matches
CL/`+` variadic semantics; the i1 check still fires for ≥2-arg forms inside
`emit-short-circuit`.

**Tests:** added `logic` (variadic 0/1/N-arg `and`/`or`) and `and-narrow` (the
3-arg narrowing proof); **117 → 119 pass.**

**Bootstrap deviation worth recording.** The design prompt predicted this change
would be bootstrap-inert (byte-identical, **no** refresh) like `_+`/`+`. That
prediction did **not** hold: renaming a *special form* (statically dispatched via
the hardcoded `(when (= hp …))` chain in the binary) is a breaking bootstrap
change — unlike **binops** like `_+`, which are *runtime-registered* via
`add-binop` at startup, so the old boot already dispatches them (which is why the
`_+`/`+` split is inert but a `_and`/`and` split is not). The fixed point
`build/nucleusc.ll == build/stage2.ll` **does** hold byte-identically after a
one-time regeneration. **Lesson: special-form renames break the boot; binop
additions do not.** (The gotcha and the 2-stage manual bridge are captured in
`context/build.md`; docs updated in `docs/special-forms.md` + `docs/macros.md`.)

## Stage 13 — Type erasure: `BoxedFn` + `(dyn Protocol)` (2026-06-27)

**Type erasure complete (TE-0 … TE-7).** 129 tests pass; `make bootstrap` is a
byte-identical fixed point.

The shared fat-pointer machine is built once and instantiated as two user-facing
types:

- **`(BoxedFn (params…) ret)`** — a spellable, fixed-size, owning, heap-boxed
  closure handle. Any `fn`/`vfn`/`mfn`/`cfn` literal assigned into a
  `(BoxedFn …)` slot is automatically heap-boxed; the fat pointer carries a
  static per-env vtable with `invoke` and `drop` slots. Enables
  `(Vector (BoxedFn …))`, `BoxedFn` struct fields, and — critically — a `defn`
  returning a boxed closure by value, closing the CE-4 env-naming gap. A bare
  `fn` pointer boxes via a synthesized per-signature forwarder thunk. Dispatch:
  `(box args…)` or `(invoke box args…)` → indirect vtable call.
- **`(dyn P)`** for an arbitrary user protocol `P` (requires `(extend T P)` on
  the source type) — erases the concrete implementation type. Enables **B2
  unbound-abstract returns** (a `defn` returning `(dyn P)` was previously
  rejected as "unknown type"; now it is a concrete 16-byte struct) and
  **heterogeneous collections** (`(Vector (dyn P))`). Dispatch: `(method-name
  box args…)` → indirect vtable call.

Both types are `Drop`-conforming (shared `@__boxedfn_drop` thunk); neither
requires a new calling-convention (both ride the CE-3 ABI-COERCE2 16-byte
by-value-struct path). Conformance admission is unified: structural for
`BoxedFn` (env `invoke` signature match), nominal `extend` for `(dyn P)`.
All TE phases were byte-identical (no bootstrap refresh needed): the compiler
itself boxes nothing, so zero box IR is emitted during self-compilation.

The CE-4 "design exploration only" designation is fully superseded; the Stage 9
rung-5 `(dyn Protocol)` deferral is implemented. v1 scope limits: single-method
protocols only for `(dyn P)`; no `clone` on boxes (move-only); process-default
libc allocator only (no per-box `AllocHandle`); `BoxedFn`/`(dyn P)` public
`defn`s excluded from `--emit-cheader`. Detail: [stage13/progress.md](stage13/progress.md).

New iterators so the (forthcoming) combinators reach more shapes:

- **CStr byte/char iterators** (`lib/strview.nuc`) — `cstr-bytes`/`cstr-chars`

logical element is a pointer or struct yield it cast to `i64` — the
`I64ArrayIter` precedent — and the consumer recovers it with a `cast`.
Examples: `examples/listiter-test.nuc`, `examples/cstr-fold-test.nuc`,
`examples/split-iter-test.nuc`.

## Known constraints / gotchas

- **`Node.car`/`Node.cdr` and macro parameters are `(raw Node)`** (were untyped `ptr`). This lets macros and AST-walking code chain member access cast-free — `(p car)`, `((p cdr) car)` — instead of `((cast ptr:Node p) car)`. Existing `(cast ptr:Node …)` on node values stays valid (a no-op `ptr`↔`(raw Node)` reinterpret) but is no longer needed. **Resolved** ([stage14/macro-conditional-casts.md](stage14/macro-conditional-casts.md), MC-1…MC-4 all done): a shared `type-join` now absorbs a bare, elem-less `ptr` branch (quasiquote/`gensym`/`null` results) into the typed side's element type at pkind `raw` — so a `cond`/`if` mixing `(raw Node)` with a bare `ptr` branch joins to `(raw Node)` with **no cast**, and quasiquote/`gensym` results are themselves now typed `(raw Node)` rather than bare `ptr`. Pointer *kind* was never actually a collapse source — kinds meet via `pkind-meet`. Only branches of genuinely different *element* types (`(raw Node)` vs `i32`, or two different struct types) still collapse the join to `void`, which remains a real type error (`let`/`set!` `init type mismatch`, or a macro whole-body `cond` silently returning `null`). All vestigial `(cast ptr:Node …)`/`(cast ptr …)` casts have been deleted from `lib/macros.nuc`. See [docs/macros.md](../docs/macros.md) and [docs/types.md](../docs/types.md).
- Variadic arithmetic macros now live in `lib/macros.nuc` and are auto-prepended via `lib/prelude.nuc`; binary primitives are `_+ _- _* _/`.
- Macro JIT names collide after sanitization if two macros share the same non-alphanumeric character; fixed by appending macro index (`__macro_<sanitized>_<index>`).
- REPL `defn` redefinition uses thunk indirection (`@foo` → load `@foo.tgt` → call `@foo.impl.<N>`) because pure resource-tracker swap leaves cross-module call sites with stale baked-in addresses. See `design/stage6-redefinition.md` "Result".
- **REPL `defmacro` segfaults or hangs.** Typing a `defmacro` form (e.g. `(defmacro triple (x) (quasiquote ...))`) at `build/nucleusc -i` segfaults or hangs the REPL. Found while smoke-testing the RV-0 repl.nuc triple fix; reproduced identically on the pre-existing baseline compiler via `git stash`, so it is a latent, previously-undocumented bug, not a regression from that change. Not yet root-caused — a future session should investigate the REPL macro-JIT path (`src/repl.nuc`).
- **Top-level dispatch does not expand user macros.** The compiler's top-level form dispatch (the `case hp` block in `src/nucleusc.nuc`) matches literal head symbols (`defn`, `defvar`, `fn-attr`, …) *before* any macro expansion runs — macro expansion only happens for forms nested inside a function/macro body. A top-level invocation of a user `defmacro` (even one expanding to a single `defn`) therefore dies `error: unknown top-level form`, not a successful expansion. This rules out macro-based top-level definition sugar (e.g. a `defisr` macro wrapping several sibling top-level forms) without a dedicated top-level macro-expansion pass. Confirmed twice independently: once during Stage 14 AVR-5 (design/stage14/avr-targets.md §5), where the design's sketched `(defisr <vector> …)` macro was found not implementable for exactly this reason, and again by a separate verification pass reproducing the same minimal-macro failure. Not a bug — an architectural property of the current dispatch loop — but worth knowing before designing any future top-level sugar as a macro rather than a compiler-recognized directive (the `fn-attr` directive is the precedent for the latter path).
- **Binop `node-type` mistypes a literal-left, typed-non-literal-right operand pair. RESOLVED (Stage 15 W2a, [stage15-stress-test/literal-typing.md](stage15-stress-test/literal-typing.md)).** The fix: the type rule now lives in one shared function, `binop-result-type` (`src/nucleusc.nuc`), called by both `binop-coerce` (emit) and `node-type-call` (the type pass), so a binop's inferred type is the *unified* operand type and is symmetric in operand order. Verified against this bullet's own repro: `(defn f (x:ui8):ui8 (return (_+ 1 x)))` no longer emits the malformed `%t3 = trunc i32 %t2 to i8` (the committed boot compiler still does). `lib/avr.nuc`'s local `(unsafe/cast ui8 1)` workaround is now redundant but was left in place (harmless, and untouched by W2a's scope). Original report follows. `(defn f (x:ui8):ui8 (return (_+ 1 x)))`-shaped code (a bare int literal as the binop's *left* operand against a typed, non-literal *right* operand) mistypes in `node-type-call`'s binop typing (`src/generics.nuc`), which reports the literal's default `i32` instead of adapting to the right operand's type — while `emit` correctly adapts the literal. When the result flows into a coercion (return/let-init/typed arg) this manufactures a malformed `trunc i32 <i8-value> to i8`. General, not AVR-specific — hidden in ordinary code because the literal is usually on the right (`(_+ x 1)`); surfaced during AVR-4 (`lib/avr.nuc`'s `bit-mask`, `1 << bit`, where `shl` forces the literal left), worked around locally there with an explicit `(unsafe/cast ui8 1)` rather than fixed at the root. Root fix: adapt to the non-literal operand rather than always operand 0 in the binop type-check, then re-converge the bootstrap. Independently reproduced and confirmed by a separate verification pass: compiling `(defn f (x:ui8):ui8 (return (_+ 1 x)))` and inspecting the emitted IR directly confirms the exact malformed instruction (`%t3 = trunc i32 %t2 to i8` where `%t2` is already `i8`); candidate for AVR-6/AVR-7 or a standalone fix.
- **`lib/hash.nuc` has a lossy `i64→usize` cast that dies on AVR's 16-bit `usize`.** `lib/hash.nuc:82` casts an `i64` hash value down to `usize` unconditionally; on hosted targets `usize` is 64-bit so the cast is a no-op, but on AVR `usize` is 16-bit (per AVR-2's `ptr-int-type`), so the same cast is a genuine narrowing the compiler correctly refuses. This blocks any AVR program that imports `lib/hash.nuc` (directly or transitively via `HashMap`/`HashSet`) before it ever reaches AVR-6's function-value/`dyn` diagnostics — found while building an AVR-6 `dyn` test fixture (`examples/dyn-protocol.nuc` couldn't be used for this reason; a minimal hash-free fixture was substituted). Not yet fixed — a future AVR-2/AVR-7-flavored follow-up should narrow the hash computation itself (e.g. truncate/fold to `usize`'s actual width explicitly) rather than relying on the illegal implicit cast.
