## Nucleus build flow

- `make` compiles `src/nucleusc.nuc` using the committed bootstrap binary `bin/nucleusc`, producing `build/nucleusc` (the self-hosted compiler). The build also compiles `src/repl_shim.c` (setjmp/longjmp wrapper for REPL error recovery) and links it with the compiler.
- `src/nucleusc.nuc` source-imports `src/repl.nuc` (REPL implementation) and `src/cheader.nuc` (C header parsing + `--emit-cheader`). These are pure file moves: the REPL and cheader code depend on compiler internals (`g-globals`, `emit-*`, type registry), and source imports inline forms into the same translation unit. The repl shim FFI (`repl_try`/`repl_throw`/`repl_print_f*`) is declared in `nucleusc.nuc` itself rather than in `repl.nuc`, because non-REPL sites (e.g. `src/reader.nuc`, `jit-*` in `nucleusc.nuc`) call `repl_throw` and need the declaration before `(import repl)` is reached.
- **`src/reader.nuc` `(import error)`s** (Stage 10 E4): the reader's recoverable syntax errors are `!T` returns (`read-program`/`read-form`/`lex-*` return `(Result ptr Err)`), not `repl_throw`/`exit`. This transitively pulls the error library (`try`/`with-handler`/`g-handler-top`/`err-find-handler` + a one-entry `deferror` descriptor table) into the compiler binary — harmless (no non-`!` `err` sites exist in the compiler, so no handler check is ever emitted), but it means **the reader is no longer standalone-compilable** in the abstract (it already wasn't — it references `g-source-path`/`g-mono-context`/`g-interactive` defined in `nucleusc.nuc`). **Stage 15 W9 item 1 acted on that: the file moved `lib/reader.nuc` → `src/reader.nuc`**, since `lib/` is exactly the set `make lib-objs` compiles standalone. The move is IR-neutral (import resolution searches the importing file's own directory first, so `(import-use reader)` from `src/nucleusc.nuc` finds it either way); `COMPILER_DEPS` in the Makefile was updated with it. `die-at` stays as the panic tier; the new `report-at` is `die-at` minus the throw/exit, used so reader diagnostics keep their path:line context even though `Err` carries only an id. The batch driver wraps reads in `read-program-or-die` (`exit 1` on `err`); the REPL `match`es and recovers.
- **`compiler-init` no longer exists (Stage 15 W8 G-5).** Every global it built is now built by its own `defvar` initializer: the constants by the loader, the rest by `@__nucleus_init` via `llvm.global_ctors`, i.e. **before `main` is entered**. What survives is one call, `(target-init)`, made directly from `main` right after the argv loop and from `repl-main` — it is the one genuinely special case, because it reads `--target=`/`--mcpu=` and derives five globals from one call.
  - The consequence for the compiler's own state: **every compiler collection is arena-backed, uniformly.** The old split this file used to document — `add-include-path`/`add-link-arg` run during argv parsing, which preceded `compiler-init`, so the `-I`/`-l` vectors were silently libc-`malloc`-backed for their whole lifetime while everything else was arena-backed — is gone. `g-arena-alloc` is now a *constant* `(AllocHandle ALLOC-ARENA null)` applied by the loader, so there is no "before init" window at all.
  - The property that made that split invisible is still true and still worth knowing: `AllocHandle` zero-fills to `kind=ALLOC-LIBC` (0) and `vector-init-alloc` copies the handle **by value** at construction, so a collection built through a not-yet-armed handle stays libc-backed forever even after the global is fixed. That failure mode is **silent** — which is why `assert-compiler-arena-backed` (`src/nucleusc.nuc`, called from `main` and `repl-main`) asserts it positively on every single compile, and why `examples/g5-arena-backed.nuc` pins the same property at the language level. If you ever add a global collection, check it against the *vector's copied* handle, not the global's current value.
- **Known compiler limitations (discovered during M6 String work):**
  - **`(Maybe StrView)` fails in JIT/macro modules** — the macro-expansion JIT module doesn't include struct type definitions from imported libraries, so `%StrView` is undefined in the JIT IR. Workaround: use a done-flag struct API instead of `(Iterator StrView)` conformance. Root cause: JIT module doesn't replay imported struct definitions.
  - **`!void` (error-union with void payload) is not supported** — `(return (ok))` inside a `!void`-returning function errors "arm 'ok' takes a different number of fields". Workaround: use `!i32` and return 0 for success. Fix: teach `emit-return` about void-payload `ok`.
  - **Struct return through `Result`/`!T` yields zeroed fields** — when the payload type `T` is a struct (e.g. `!StrView`), the struct fields are all zero after `(try ...)` unwrapping. Root cause: `emit-struct-ret` / Result ABI interaction. Workaround: return `!ptr:StrView` (heap pointer) instead of `!StrView`. Fix: investigate sret interaction with Result unwrap.
- `boot/nucleusc.ll` (the committed LLVM IR) is the actual bootstrap source of truth. `bin/nucleusc` is a derived ELF binary, `.gitignore`d and NOT tracked in git (removed from tracking in `6fa1422 Remove binary - LLVM IR is the bootstrap mechanism`) — every checkout rebuilds it locally from `boot/nucleusc.ll`.
- If `bin/nucleusc` is missing or can't execute (e.g. LLVM version mismatch), `make` auto-rebuilds it from `boot/nucleusc.ll`. You can also force a rebuild with `make boot-binary`.
- `./build.sh examples/foo.nuc` runs `make`, then compiles the source file with `build/nucleusc`. Compile-time output goes to **stderr**; IR to **stdout**.
- `make test` runs `tests/run-tests.sh`, which diffs each example's **runtime** output against `tests/expected/<name>.out`. A compile failure is caught (not ignored): `run_example` checks `build.sh`'s exit code explicitly and, on failure, emits `FAIL <name> (compile error)` followed by the captured nucleusc stderr, indented under the FAIL line. The `test` target also `rm -rf`s `build/out` first, so a stale binary from a prior run can never mask a fresh compile failure (the diff would otherwise pass against the old output).
  - **Tests run in parallel.** Each test group (per-example, per-REPL-session, per-target-triple, per-long-ABI-check, the two sub-scripts, and each fixture/rejection block) is a self-contained unit dispatched as a background job, bounded by `NUCLEUS_TEST_JOBS` (default `$(nproc)`, plain bash `wait -n` semaphore — no GNU parallel). Each unit buffers its `PASS`/`FAIL` line(s) + diff body to a per-unit file; after all jobs join the files are replayed in dispatch order, so printed output is deterministic and matches the old serial top-to-bottom order. Override with e.g. `NUCLEUS_TEST_JOBS=1` for a serial run (useful for isolating a race). Measured 2026-08-09 on the 16-core host at 463 tests: **~144 s serial → ~36 s parallel (4×)**. Earlier figures in this file (`~60 s → ~8.5 s`, "7× slower") were stale by several fixture batches.
  - **Count with the parallel default; do not reach for `NUCLEUS_TEST_JOBS=1` to get a reliable number.** The per-unit buffering above makes interleaving impossible by construction, so the counts agree: three consecutive parallel runs and one serial run of one tree all reported 463 PASS / 0 FAIL. Stage 15 W9 item 10 recorded PASS counts as "unreliable by ±1" and every verification entry from G-2 onward then used `NUCLEUS_TEST_JOBS=1` to count — but that evidence predates the buffering (`cb864fa`, 2026-07-05) and the item was never re-verified. It is closed; the serial run costs 4× for nothing.
  - Each unit is isolated in its own subshell. `run_example` guards its `./build.sh` call with an explicit exit-code check (not bare under `set -e`), so a compile failure prints a `FAIL <name> (compile error)` line plus the compiler's stderr instead of dying silently. Other unit functions that can still die early (unexpected crashes, not ordinary compile errors) leave an empty result file, which the replay flags as a global failure (exit 1) with **no `PASS`/`FAIL` line** — the only signal is a missing line; run the suspect example through `./build.sh` directly to find the culprit.
- `make bootstrap` does the fixed-point test: stage1.ll == stage2.ll.
- The compiler emits **opaque-pointer** LLVM IR (`ptr`, not `i8*`/`i32*`). A target descriptor is the single source of truth for the "a pointer is i64" assumption: `g-target-triple` and `g-target-ptr-bytes` (default 8) drive type sizes/alignments, `sizeof`, and `size_t` width. Rather than being hardcoded, they are **derived from LLVM at startup** — `target-init` → `make-target-for-triple` pulls the triple, datalayout, and pointer size from LLVM (host by default; overridable with `--target=<triple>`), so emitted IR runs on whatever target is selected. Backends for non-host triples must be registered before selection; `targets-init-all` registers X86, AArch64, ARM, AVR, and RISCV, so `--target=` resolves for x86_64/i386/aarch64/arm/avr/riscv64 across Linux/Darwin/Windows triples. It is called exactly **once**, at startup, from `target-init` (itself called from `compiler-init`, which runs before batch `main`, CT-JIT (`emit-toplevel-forms`), and the REPL (`repl-main`) alike) — process-wide LLVM target registration is idempotent and global, so `jit-ensure-init` and `compile-and-link` do *not* re-register backends (their former inline per-call `LLVMInitializeX86*` blocks were dead code, deleted in RV-1). A `Target` descriptor also carries `cpu`/`features`/`abi` (all `""` for host/hosted triples, so their IR/`LLVMCreateTargetMachine` args are unaffected); non-empty defaults for a given triple are supplied by triple-keyed resolver functions (`cpu-for-triple`, `features-for-triple`, `abi-for-triple` in `src/nucleusc.nuc`, beside the pre-existing `reloc-for-triple`) — follow this pattern when a future target needs a non-empty default rather than hardcoding it inline. When `abi` is non-empty, `assemble-module-ir` emits a `!llvm.module.flags` block pinning `target-abi` — the compiler's first (and so far only) module-flags emission; it's conditional on non-empty `abi` specifically so every existing target's `--emit-llvm` output stays byte-identical.
- Two descriptors exist: `g-target` (output target, honors `--target=`) and `g-host-target` (always native). JIT-bound modules (compile-time bodies, `defmacro`, REPL eval) always emit under the **host** triple (`g-host-target`) — the JIT runs in this process, so its modules must match host layout — while the final batch output module emits `g-target`'s `datalayout` + `g-target-triple`. The hand-written `__cons`/`__append` IR in `emit-qq-helpers` (the Node-cons-cell allocator) is derived from the `Target` descriptor rather than hardcoded: size = `16 + 3*ptr-size`, and each field's `align N` = `gcd(struct-offset, ptr-align)`. `ptr-int-ir`/`ptr-int-type` (`src/type-utils.nuc`) similarly select `i16`/`i32`/`i64` from `g-target-ptr-bytes` rather than a binary 4-vs-8 check — both fixed in AVR-2 to be correct at `ptr-size=2` (AVR), reproducing the prior literals byte-for-byte at `ptr-size=8` (host).
- **Aggregate ABI (Stage 8 Phase C, x86_64 System V; extended Stage 14 AVR-7):** struct-by-value parameters and returns are lowered to the platform C ABI by `abi-classify` (eightbyte classification → `byval` / `sret` / register coercion), threaded through `emit-defn`, the `declare` emitter (`emit-nuch-declare-import`), `emit-call-with-args`, and `emit-return`/`emit-struct-ret`. Only `TY-STRUCT` is ever non-`DIRECT`, so scalar/pointer codegen is byte-identical and the bootstrap (which passes only pointers) never exercises it; `make abi-test` is the real gate. Non-x86_64 ABIs plug in behind `abi-classify` keyed on `g-target-triple` (`abi-is-aarch64`, `abi-is-avr` — string-prefix/substring predicates, not the `Target` descriptor): aarch64 and `avr` both skip `byval` and pass `ABI-MEMORY` values as a plain pointer instead; `avr` additionally routes **every** aggregate (any size) through `ABI-MEMORY`, since eightbyte classification's 8-byte-register-chunk model has no analogue on an 8-bit target — `abi-classify` bypasses it entirely for `avr` rather than adapting it. Other non-x86_64 ABIs (e.g. `riscv64`'s native struct-passing convention) remain deferred.
- **AVR link driver + container toolchain (Stage 14 AVR-0/AVR-3, workstream complete as of AVR-8):** `compile-and-link` keys the link-driver command on the triple — `avr-gcc` (not `clang`) for any `avr` triple, since avr-gcc alone knows the device linker scripts, crt/vector table, and libgcc; `--linker=` overrides the driver regardless of triple. The container toolchain (ground-verified AVR-0, installed via Arch `pacman` in this container rather than the Debian `apt` line the original design sketch named): `avr-gcc` 14.2.0, `binutils-avr` 2.43.50, `avr-libc` 2.2.1 (≥ 2.2, so the Microchip DFP `-B` fallback is never needed for the AVR-Dx reference device), `simavr` 1.6 (the AVR simulator — covers ATmega328P, not the ATtiny1634/AVR-Dx reference devices, which have no simulator in this container). `make avr-test` (`tests/run-avr-test.sh`) is the AVR-specific test harness — compiles/links/budget-checks the four `examples/avr-*.nuc` programs plus a `simavr` behavioral smoke test — gated on `avr-gcc`/`simavr` and kept separate from the host-only `make test`/`make bootstrap`. See [docs/avr.md](../docs/avr.md) for the full flag reference, a worked two-device walkthrough, the v1 language/library profile, and the MMIO/ISR idioms.
- **RISC-V (riscv64-linux) cross link + qemu test lane (Stage 14 RV-2):** the same `compile-and-link` triple-keyed driver selection — a `riscv64`-prefixed triple (`(strncmp g-target-triple "riscv64" 7)`, beside AVR's `avr` check; `--linker=` still overrides) selects `riscv64-linux-gnu-gcc`, the Debian cross toolchain that carries the riscv64 sysroot + crt startup objects. Unlike AVR, riscv64 is a hosted glibc target: PIC stays and **no** `-mmcu`-equivalent flag is added — the driver name is the only change. `make riscv-test` (`tests/run-riscv-test.sh`, modeled on `run-avr-test.sh`) compiles each `examples/*.nuc` that has a recorded expected output via the real link path (`--target=riscv64-unknown-linux-gnu -o`, no `--emit-llvm`/`-c`), runs it under `qemu-riscv64 -L /usr/riscv64-linux-gnu`, and diffs stdout — opt-in, not part of `make test`/`make bootstrap`. **Two-stage SKIP gate** (important): checking only `command -v riscv64-linux-gnu-gcc` is insufficient — this container has `libc6-riscv64-cross` (runtime shared libs) but **not** `libc6-dev-riscv64-cross` (crt startup objects + headers), so a link fails `cannot find Scrt1.o`. After the `PATH` check, the harness runs a **capability probe** (drive the compiler's link path on `examples/hello.nuc`, check it *succeeds*); on the crt-shaped failure it SKIPs cleanly (exit 0) with a pointer to the missing package instead of FAILing every example. The full gate runs unchanged the moment the container gains that `-dev` package (a Dockerfile change reachable only from the user's interactive session, like AVR-0's). riscv64's aggregate-passing ABI is still deferred (RV-3) — scalar/pointer interop is exact; do not cross-run FP-struct-by-value C interop until then.
- **`llc` on riscv64 textual IR needs an explicit `-mattr` (the features cliff, outside the compiler's own codegen path):** the compiler's own `-c`/`-o` object emission and the JIT both pass `+m,+a,+f,+d,+c` into `LLVMCreateTargetMachine` via `features-for-triple`, but a `--target=riscv64-... --emit-llvm` textual `.ll` does **not** bake those features in anywhere — they're a `TargetMachine` construction argument, not IR content (the `target-abi=lp64d` module flag *is* baked into the IR, but features aren't). Anyone hand-feeding that `.ll` through a bare `llc` (no `-mattr=+m,+a,+f,+d,+c -mtriple=riscv64`) gets the same silent RV64I soft-float fallback (`__muldi3`/`__adddf3` libcalls, integer-register float ABI) that RV-1 exists to prevent inside the compiler. `run_riscv_emit` (`tests/run-tests.sh`) is the reference invocation for the correct flags.
- Top-level `defvar` globals are emitted to `g-def-stream` (def-bufp), not `g-decl-stream` (decl-bufp). CT and macro JIT modules concatenate `g-decl-bufp` plus their own private decls/defs; if defvars went to decl-bufp they would be redefined in every JIT module and collide with the host process's symbols (which the dylib generator also exposes). External calls from JIT modules into host-defined globals (e.g. `g-intern-cap`) resolve through the dylib search generator instead. Adding new global state that lives in code reachable from CT/macro bodies must follow this same routing.
- The self-hosted compiler and its bootstrap artifacts are linked against the system LLVM (19+). The Makefile auto-detects `llvm-config` (trying versioned names like `llvm-config-21`, `llvm21-config`, and common Alpine paths), preferring `--link-shared` for the monolithic shared lib, falling back to static component libs, then to bare `-lLLVM` if neither works. A diagnostic line (`LLVM: config=... ldflags=... libs=...`) prints at build time so link failures can be diagnosed remotely.
- **`-O`N` currently sets only the LLVM *codegen* level** (instruction selection / register allocation / scheduling), passed to `LLVMCreateTargetMachine` in `compile-and-link`. The LLVM **middle-end** pass pipeline (`mem2reg`, `instcombine`, LICM, GVN, vectorizers) is **not yet wired**: `compile-and-link` goes straight from `LLVMCreateTargetMachine` to `LLVMTargetMachineEmitToFile`. The PassBuilder C API (`LLVMRunPasses`, `LLVMCreatePassBuilderOptions`) is already declared in `src/llvm.nuch` (in the linked `libLLVM-19.so`, no Makefile/link change needed), so wiring it in is the open optimization work tracked in `design/stage999-future.md`. `--emit-llvm` always emits **unoptimized** textual IR, which also means the bootstrap fixed-point check (which goes through `--emit-llvm`) is structurally immune to optimization-level changes.

## `make layout-test` / `make abi-test`: what each one can and cannot catch

Two different gates against the platform C ABI, and they do not overlap.
`make layout-test` (`tests/layout/`) compares `sizeof` and every field offset —
it catches a wrong *size or alignment*. `make abi-test` (`tests/abi/`) links a
Nucleus caller against a `cc`-compiled callee — it catches a wrong *calling
convention*. A by-value struct can have byte-identical layout on both sides and
still be passed in the wrong register class, which only `abi-test` sees
(Stage 15 W8 G-2's `struct { float v[2]; }`: 8 bytes either way, but SSE vs
INTEGER). Run both after any change to `abi-classify`, `abi-sizeof`,
`abi-alignof` or `abi-class-eightbyte`.

Extending them has one non-obvious constraint each. **`tests/layout/structs.h`
is imported by `layout.nuc` as a C header**, so a shape the Nucleus C-header
parser cannot represent (an array declarator, a bitfield) cannot live there
unguarded — it would register as an opaque `ptr` and collide with the Nucleus
side's own `defstruct`. G-2's array shapes therefore sit behind
`#ifdef NUCLEUS_LAYOUT_C_ORACLE`, which only `layout.c` defines, with `layout.nuc`
declaring the matching shapes itself. **`tests/abi/expected.out` must come from
an all-C reference build**, never from the Nucleus output being tested — write a
throwaway C `main` against `tests/abi/clib.c`, run it, and paste its lines in;
the print ORDER must match `interop.nuc`'s, since the harness diffs.

## Windows build (Phase F, untested on this Linux host)

- `build.ps1` is the PowerShell counterpart of the Makefile/`build.sh` flow: compile `repl_shim` → ensure a boot compiler exists (build from committed Windows boot IR if `bin\nucleusc.exe` is missing) → self-host (`--emit-llvm` → clang link). `bootstrap.bat [mingw|msvc]` is a cmd.exe wrapper over `build.ps1 -Bootstrap`.
- `-Toolchain mingw` (default, fully open source: `x86_64-pc-windows-gnu`, clang+LLD, links `-Wl,--export-all-symbols` for the JIT) and `-Toolchain msvc` (`x86_64-pc-windows-msvc`, clang → `link.exe`/`lld-link`). Both drive `clang` and use `llvm-config` (`orcjit core irreader` + `--system-libs`); only triple, boot IR, and export flag differ.
- `build.ps1` passes `--target=<triple>` on every self-host step so the emitted triple is deterministic (independent of how the host LLVM names itself) and matches the committed boot IR, keeping the fixed-point check honest.
- **Do not redirect native stdout with PowerShell `>`** — Windows PowerShell 5.1 re-encodes it as UTF-16-with-BOM, corrupting the `.ll`. `build.ps1` uses `Start-Process -RedirectStandardOutput`, which preserves the child's raw bytes.
- Win64 aggregate ABI at the C boundary is **not** correct yet (Phase C did SysV only); the compiler itself never hits this because its own IR passes only pointers (no real `byval`/`sret`), so it still bootstraps on Win64.

## Merging a branch merges `boot/nucleusc.ll` **textually** — verify it still builds

`boot/nucleusc.ll` is a ~100k-line generated file that git will happily
three-way merge. A merge can keep *both* sides' copies of a function, producing
an LLVM module with a duplicate definition that `clang` rejects
(`invalid redefinition of function '<name>'`). This actually happened at
`04c55ec Merge stage14`, which duplicated `@emit-keyword`; the duplicate also
carried a `@.str.N` reference from the *other* side's string pool, so the second
copy indexed `"_get"` (5 bytes) through a `[15 x i8]` GEP. Nobody noticed for
two commits because `bin/nucleusc` is `.gitignore`d: existing checkouts kept
using a locally built pre-merge binary, and only a **fresh checkout** (or a
`rm bin/nucleusc`) hits the `make boot-binary` path that actually parses the IR.

After any merge that touches `boot/*.ll`:

1. `rm -f bin/nucleusc && make` — forces the rebuild-from-IR path.
2. Duplicate check: `grep -oE "^define [^@]*@[-A-Za-z0-9_.$]+" boot/nucleusc.ll | sed 's/.*@//' | sort | uniq -d` must print nothing.
3. String-pool consistency: every `[N x i8], ptr @.str.M` reference's `N` must
   equal the `[N x i8]` in `@.str.M`'s definition. A mismatch means a block came
   from the other merge side. (A short python scan over the file is enough; one
   mismatch is how the `@emit-keyword` duplicate was localized.)

Prefer regenerating the file from a known-good compiler over hand-editing it —
but a surgical delete of a provably stale duplicate is a legitimate repair when
the merge damage is confined and verified by (2) and (3).

## Updating bootstrap artifacts

Run `make update-bootstrap` **only at a stable milestone**:
- All tests must pass (`make test`)
- Bootstrap fixed-point must hold (`make bootstrap`)
- The compiler must be in a usable, non-broken state

This updates `boot/nucleusc.ll` (IR), `bin/nucleusc` (binary), **and** the Windows boot IRs `boot/nucleusc-x86_64-windows-{gnu,msvc}.ll` (via `make windows-boot`) from the current `build/nucleusc`. Never update them with failing tests or mid-feature work. The Windows IRs are regenerated together with the Linux one so all boot flavors stay in lock-step (cross-emitted on this Linux host with `--target=`; a fresh Windows checkout has no compiler to bootstrap from, so it needs committed Windows IR exactly as Linux needs `boot/nucleusc.ll`).

**After a codegen change, `make bootstrap` reports a spurious diff until the boot binary is converged.** `make bootstrap` diffs `build/nucleusc.ll` (emitted by the *old* `bin/nucleusc`) against `build/stage2.ll` (emitted by the *new* `build/nucleusc`); if your change alters emitted IR, these differ by construction even though the new compiler is self-consistent. To converge: `make clean && make && make update-bootstrap && make clean && make && make bootstrap`. The first round builds + installs the new compiler as the boot binary; the second round rebuilds both `.ll`s from it so they match. To check self-consistency directly without touching committed artifacts, compile `src/nucleusc.nuc` with `build/nucleusc`, build that IR into a stage2 binary, recompile, and diff the two IRs (they must be identical — codegen is deterministic).

**Breaking changes the OLD boot can't bridge (chicken-and-egg).** The converge cycle above assumes `make` succeeds — i.e. the committed `bin/nucleusc` can still compile the new `src/`. A change can be too breaking for that, so `make` fails *before* you can converge. The two root causes seen so far:
- **Renaming a special form whose name a new `defmacro` wants to shadow.** `guard-name-kind` (nucleusc.nuc) calls `die-at` when a `defmacro` name is already `NK-SPECIAL` (checked first via `special-form-named`/`g-special-form-set`). The OLD boot's runtime set is built from *its own* source, so it still has the old name → it rejects the new `(defmacro <old-name> ...)`. (Stage 13 variadic `and`/`or`: adding `(defmacro and ...)` while the OLD boot still has `and` as a special form died with "'and' already names a special form".)
- **A new special-form dispatch symbol the OLD boot doesn't know.** Special forms dispatch through the *static* `(when (= hp 'foo) …)` chain hardcoded in the binary, so the OLD boot can't lower a form whose head is a brand-new special-form symbol. This is unlike **binops** (`_+ _- _* _/`), which are *runtime-registered* via `add-binop` at startup — the OLD boot already dispatches them, which is why the `_+`/`+` split is bootstrap-inert but a `_and`/`and` split is not.

A third root cause, found in Stage 15 W8 G-5: **a new `defvar` initializer form
the old boot's `defvar-init-ir` cannot render.** The committed boot predates
G-1/G-3, so the moment `src/` gained runtime initializers it died *"defvar: init
must be a literal"* on the very first `make`. The general shape is "the source
now uses a language feature the committed boot does not have", and it is worth
recognising early because the standard converge cycle above **silently assumes
the first `make` succeeds**. When the feature landed in an *earlier, already
converged* commit — which is the common case for a staged design — there is a
shortcut over the 2-stage dance below: the current `build/nucleusc` already has
the feature, so use it directly as C0 (compile the new source with it, link, and
verify the result is a fixed point by having it compile itself) and only then
`make update-bootstrap`. Nothing has to be elided.

When `make` can't bridge, do a **2-stage manual bootstrap** (no edit to the converge cycle needed once converged): (1) temporarily elide the offending construct from the source and `make` — the OLD boot builds an intermediate compiler C0 that has the new dispatch but not the clashing defmacro; (2) restore the full source and compile it *with C0* (`build/nucleusc --emit-llvm src/nucleusc.nuc > build/c1.ll`), link that into `build/nucleusc` (=C1), then regenerate `boot/nucleusc.ll` + `bin/nucleusc` (+ Windows IRs via `--target=`) from C1. Then the normal `make clean && make && make bootstrap` holds the fixed point. Confirmed for the variadic-`and`/`or` change: post-convergence `build/nucleusc.ll == build/stage2.ll` byte-identical, `make test` green.

## Import system

- The compiler auto-imports `lib/prelude.nuc` at the top of every batch compilation. The prelude provides the `Node` struct, the `NODE-*` enum, and `(import macros)`, so variadic `+ - * /`, `if`, `when`, `dotimes`, etc. are available without explicit imports. To opt out, make `(exclude-prelude)` the first top-level form in the file. **Freestanding targets (AVR) must opt out:** the prelude force-emits `lib/node.nuc`'s intern/arena runtime, which references host-only libc symbols (`perror`, `malloc`) that don't exist in freestanding avr-libc — an AVR fixture that doesn't `(exclude-prelude)` fails at the `avr-gcc` link step with undefined-symbol errors, not a compiler error. See `tests/fixtures/avr3-link.nuc` / `tests/fixtures/avr2-16bit.nuc` for the pattern (only compiler-builtin special forms and binops, no prelude-provided helpers).
- The compiler source itself starts with an explicit `(import prelude)` so that the bootstrap fixed-point holds: `bin/nucleusc` (no auto-prepend) processes the explicit import in the same source position as `build/nucleusc` (auto-prepend, dedup'd against the explicit one).
- `(import name)` resolves `name.nuc` or `name.nuch` by searching: (1) directory of the importing source file, (2) `lib/` relative to cwd, (3) directories specified with `-I`. `.nuc` is tried first.
  - **Gotcha:** because the importer's own directory is searched first, a bare `(import-use list)` from `examples/foo.nuc` resolves to `examples/list.nuc` (which has its own `main`), **not** `lib/list.nuc`. When an example needs a library whose basename collides with a sibling example, import by path: `(import-use "lib/list.nuc")` (resolves from cwd = repo root).
- Source imports (`.nuc`) are source inlines — the imported file's forms are read, parsed, and processed into the current compilation's IR streams.
- Header imports (`.nuch`) emit LLVM `declare` for functions (resolved at link time from `.o` files), and process `defstruct`, `defconst`, `defenum`, and `defmacro` normally.
- Duplicate imports (same resolved path) are silently skipped.
- Circular imports are **legal** (Stage 15 W1d, Option 2): `do-import` skips a re-entry of a path that is already on `g-importing` instead of erroring, so each file is emitted at most once, at first reach. Cycles of any length work, as does self-import. What a cycle does *not* carry — because it is emission-time, and a cycle member's body is emitted before the rest of the file it back-imports — is macros, `deferror` ids, `extern` declarations, struct/union layouts, and `prefix/name` aliases; each is refused with a located diagnostic naming the cycle (see `docs/toplevel.md`). **`defconst`/`defenum`/`defvar` names came off that list in Stage 15 W8 G-0**: `prescan-value-names` registers them on the whole-graph walk, so a cycle carries value names as well as signatures.
- Reader state (`g-src`, `g-pos`, `g-line`, `g-source-path`, `g-peek`, `g-peek-valid`) is saved/restored around each import.
- C header imports: `(import "stdio.h")` runs `clang -E -x c -include stdio.h /dev/null`, parses extern function declarations from the preprocessed output, registers them in `g-globals`, and emits LLVM `declare` statements. Handles function pointer parameters, `__attribute__`, `__asm__`, variadic functions, and struct/typedef skipping.
  - **musl compatibility (Alpine ARM64):** musl's libc headers omit `extern` on function declarations (valid C — file-scope functions are implicitly `extern`), while glibc includes it. The C header parser now tries `c-parse-func-decl` for any non-struct/union/typedef token, not just `extern`. `c-parse-type` already skips `extern`/`static`/`inline` internally, so both styles parse identically. Also skips `_Noreturn` (C11 keyword used by musl for `exit` and other noreturn functions).
  - **Null pointer printing portability:** `printf("%p", NULL)` is implementation-defined: glibc prints `0`, musl prints `(nil)`. Tests that compare output must cast pointers to integers before printing (e.g., `printf("%lld\n" (cast i64 p))`) for platform-independent results.
- `(include stdio)` is syntactic sugar for `(import "stdio.h")` — both use C header parsing via `clang -E`. All functions from the header are imported, not just a hardcoded subset.
- The REPL pre-loads stdio.h, stdlib.h, string.h, ctype.h, and unistd.h via C header parsing at startup.

## .nuch headers and library compilation

- `nucleusc --emit-nuch file.nuc` outputs a `.nuch` header (S-expression declarations) instead of LLVM IR.
- `nucleusc --emit-cheader file.nuc` outputs a C header (`.h`) with `#pragma once`, `typedef struct`, function prototypes, `#define` constants, and enums.
- `make lib-headers` generates `.nuch` for all `lib/*.nuc` files.
- `make lib-cheaders` generates `.h` for all `lib/*.nuc` files.
- `make lib-objs` compiles all `lib/*.nuc` to `.o` via `nucleusc` → `llc -filetype=obj -relocation-model=pic`.
- `make lib-so` builds `build/lib/libnucleus.so` shared library from all library `.o` files. **This one still fails** (W9 item 2): every object inlines the whole prelude closure, so e.g. `vector.o` and `combinators.o` both define `vector-oom` / `next.pIntRangeIter` and `ld` refuses. That is an open architectural question about how the prelude participates in a multi-TU build, not a defect in the per-file rules above.
- `make lib` does both headers and objects.
- **`make lib-headers` / `make lib-cheaders` write into `lib/` itself**, over the committed `lib/mathlib.nuch` and `lib/boxlib.nuch` and leaving ~30 untracked `.nuch` / `.h` files behind. Regenerate-and-diff the two committed ones; delete the rest afterwards so the tree stays clean.
- **The invariant these three targets assert is "every `lib/*.nuc` compiles as its own entry file", in all three emit modes.** Stage 15 W9 item 1 made that true and pinned it (`run_w9_lib_standalone`, `tests/run-tests.sh`). Two things it needed: the unit's ROOT file had to join `g-prescan-sigs` / `g-importing` (the auto-prelude reaches `node`/`arena`/`macros`, so compiling one of them imported the entry file itself — see conventions.md), and `--emit-nuch` stopped being exempt from the prelude, since an exported signature names imported types. A new file under `lib/` that touches compiler-private globals belongs in `src/` instead.
- Self-contained libraries (e.g. `mathlib.nuc`, `arena.nuc`, `node.nuc`) can be compiled to standalone `.o` files. `arena.nuc` declares its own globals (`g-arena`, `g-arena-used`, `g-arena-cap`) and lazily initializes on first allocation; `node.nuc` imports `arena` and uses the prelude-provided `Node` struct.
- To use a header-only import: generate `lib/foo.nuch` and `build/lib/foo.o`, then programs using `(import foo)` will find the `.nuch` and emit `declare` statements. Link the program's `.ll` against `foo.o` with clang.
